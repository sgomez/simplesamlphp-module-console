# Nodes fetch published Snapshots instead of rebuilding them

A Publication stores the Snapshot in the database as one immutable, numbered JSON document carrying a format version and a checksum, and marks it as current. A node never reads the edit tables: it fetches the current Snapshot, resolves its Secret references and writes it to local disk, where a `MetadataStore` of the module serves it. Rebuilding from the edit tables on each node was the original idea; it breaks in a rolling deploy, where old code meets a new schema, and lets two nodes derive different results from the same version.

## Considered Options

- **Rebuild from the edit tables on each node**: rejected for the reasons above.
- **Core `serialize` layout on disk**: rejected; one file per entity has no notion of a whole set, so a switch passes through mixed states, and it has no place for authsources or for the Snapshot's own version and checksum.
- **Own polling command, run from the container entry point and a crontab**: rejected; running commands inside containers is a burden on the administrator, whereas an external scheduler calling the core `cron` URL is already common practice. Installing the module must take no more than editing configuration files.
- **Checking for a new Publication from ordinary requests**: rejected; SSO would depend on the database in normal operation.
- **Console pushes to nodes**: rejected; the Console would have to know the nodes. Reading the database during SSO to detect a new Publication is forbidden by the Snapshot rule.
- **Full node status in the database** (dropped objects with reasons, source order, module version): rejected; the one question worth a shared table is whether a Publication reached every node. The detail stays on the node.

## Consequences

- Rollback marks an earlier Snapshot as current. Nodes compare against the current one, never the highest number.
- On disk each build of a Snapshot is a directory `<dir>/<n>-<b>/` of PHP files (`return [...]`, one per set and one for authsources) plus a `manifest.json`, with restrictive permissions because secrets are resolved. `b` grows with every rebuild of the same number, so a file is never rewritten in place: with `opcache.validate_timestamps=0` PHP would keep serving the old one. A `current` file names the build being served; it is switched by atomic rename and read once per request. The current and previous builds are kept. With opcache, older builds hold memory until PHP restarts.
- `manifest.json` holds what is fixed for a build (number, format version, checksum, build time, module version, objects left out with their reason). A `status.json` at the root of the directory holds what changes on every check.
- The Snapshot document holds only content, as lists sorted by entity ID or authsource id rather than maps, so the same content always gives the same bytes. Its checksum is the SHA-256 of the stored bytes. The format version rises only when an older node would misread the document without noticing: a change of the envelope, or of the meaning of an existing option. Additive changes do not raise it; an older node leaves out the object it cannot translate.
- Entities and authsources travel in the same Snapshot and are published and rolled back together.
- Running nodes learn of a Publication through the core `cron` module: a `CronEvent` listener checks for a newer current Snapshot on every tag, or only on the one named by the optional `cron_tag` option. The check is idempotent and reports its outcome in the `cron` summary. A call every minute is recommended. Behind a load balancer the scheduler must reach each node directly. The node serving the Publication request updates itself in that request, so a single-node deployment needs no `cron` at all. The module registers no commands.
- A node with no local Snapshot fetches the current one during its first request, under a local lock. This is the only case in which an SSO request reads the database. If none has been published, the node records that locally and asks no more; after a failed attempt it waits 60 seconds before trying again.
- The Snapshot table, the Node table and the one-row table holding the current-Snapshot pointer are stable contracts, so any code version can read them: migrations only add columns, nullable or with a default, and never drop, rename, retype or repurpose one; code always names its columns. An incompatible change is expressed by raising the Snapshot format version, never by altering these tables. A node whose code is older than the current format keeps its local copy, or fails if it has none; it never falls back to an earlier Snapshot.
- An unresolvable Secret reference drops only the affected entity or authsource and is logged and kept in the node's local status.
- On every check a node resolves the Secret references of the current Snapshot again and rewrites its local copy only when the result differs, so a rotated secret needs no Publication.
- Each node records in the database only its identifier (hostname unless configured), served version, last check and a flag saying it has problems. A failed write is logged and ignored. The Console highlights a node that serves another version than the current one, has not checked for 5 minutes or carries the flag; a node silent for an hour (configurable) is forgotten.
- What the problems are (dropped objects with their reason, a missing authsource fragment, the core `pdo` source in `metadata.sources`) is kept on the node's disk next to the Snapshot and shown by that node only: on its status screen, in its `cron` summary and in the core sanity check. Behind a load balancer the administrator sees which node has problems, and has to reach that node to read them.
- With the database down, a node keeps serving its local copy indefinitely.
